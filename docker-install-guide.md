This guide explains how to build and run an Ubuntu 24.04 Docker image that ships
**ROS 2 Rolling**, **Qt 6.7.2**, **Boost 1.83.0** and a full set of development
tools, with GUI and GPU support.

The provided run session also installs a **Fast DDS profile that prevents the
container from using shared memory** to transfer data between the container and
the host. Data is instead exchanged over UDP through host networking. The same
profile must be loaded on **both** the host and the container (see
[section 6](#6-why-the-session-disables-shared-memory)).

## 2. Prerequisites

- Docker installed and running.
- Qt 6.7.2 installed on the host under `$HOME/Qt` (the build script copies and
  tars this folder to produce `Qt.tar.gz`).
- `boost_1_83_0.tar.gz` present in this directory.
- An X server on the host (for the GUI session).
- Install `nvidia-container-toolkit` ([link](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html))
```bash
# Install the prerequisites for the instructions below:
sudo apt-get update && sudo apt-get install -y --no-install-recommends \
   ca-certificates \
   curl \
   gnupg2
# Configure the production repository
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg \
  && curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
    sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
    sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
# Update the packages list from the repository
sudo apt-get update
# Install the NVIDIA Container Toolkit packages:
export NVIDIA_CONTAINER_TOOLKIT_VERSION=1.20.0-1
sudo apt-get install -y \
    nvidia-container-toolkit=${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
    nvidia-container-toolkit-base=${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
    libnvidia-container-tools=${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
    libnvidia-container1=${NVIDIA_CONTAINER_TOOLKIT_VERSION}
```

## 3. How the Dockerfile is created

The image is built in a single stage from `ubuntu:24.04`:

1. **Base + non-interactive** — `DEBIAN_FRONTEND=noninteractive` prevents
   interactive timezone/keyboard prompts.
2. **Locales** — installs `locales` and generates `en_US.UTF-8`.
3. **ROS 2 Rolling repository** — adds the ROS 2 apt repository (universe +
   `packages.ros.org`).
4. **Packages** — installs build tools (`build-essential`, `cmake`,
   `ninja-build`, `clang`, `mold`), `ros-rolling-desktop`, Qt/X11 dependencies
   (`libxcb-cursor0`, `freeglut3-dev`, `libftgl-dev`), `gdal`, `zmq`,
   `sqlite3`, editors and utilities.
5. **Boost 1.83.0** — copies `boost_1_83_0.tar.gz`, extracts it and builds with
   `bootstrap.sh` + `b2 install` into `/usr/local`.
6. **ROS environment** — appends `source /opt/ros/rolling/setup.bash` to
   `/root/.bashrc`.
7. **Qt 6.7.2** — unpacks `Qt.tar.gz` into `/opt/` and sets `PATH` and
   `CMAKE_PREFIX_PATH` for the Qt toolchain.

## 4. Build the image

Recommended — one command:

```bash
./build-docker-img.sh
```

`build-docker-img.sh` copies `$HOME/Qt` into the current directory as
`Qt.tar.gz` (skipped if the folder or archive already exists), then runs:

```bash
docker build -t rqt-based-env:latest .
```

Manual equivalent:

```bash
tar -czvf Qt.tar.gz Qt
docker build -t rqt-based-env:latest .
```

> Note: the Qt archive is a few GB and the Boost build takes a while, so the
> first build is slow.

## 5. Run the session

Start the GUI container with:

```bash
./start-qt-container.sh
```

The container now boots **systemd as PID 1** (so `timedatectl`, `systemctl`,
etc. work inside). The script starts the container detached, waits for systemd
to finish booting, syncs the host timezone, and then opens an interactive shell
with `docker exec`. When you `exit`, the container keeps running; stop it with:

```bash
docker stop rqt-based-env
```

What the script does:

| Step / flag | Purpose |
| --- | --- |
| `xhost +local:docker` | Grants the container access to the local X server |
| `/sbin/init` as command | Binds systemd as PID 1 so systemd tools work |
| `--privileged` | Lets systemd mount cgroups and run its services |
| `--cgroupns=host` + `-v /sys/fs/cgroup:/sys/fs/cgroup:rw` | Shares the host cgroup v2 namespace, required by systemd |
| `--tmpfs /run /run/lock /tmp` | systemd needs writable runtime dirs |
| `--net=host` | Shares the host network stack (needed for ROS 2 UDP multicast) |
| `--ipc=host` | Shares the host IPC namespace with the container |
| `-e DISPLAY=$DISPLAY` | Passes the display through |
| `-v /tmp/.X11-unix:/tmp/.X11-unix` | Mounts the X11 socket for GUI apps |
| `--gpus all` | Enables all host GPUs inside the container |
| `--device=/dev/dri` | Exposes the DRM graphics devices |
| `-e NVIDIA_DRIVER_CAPABILITIES=all` | Enables full NVIDIA capabilities |
| `-v .../fastdds-profile.xml:/opt/ros/fastdds-profile.xml:ro` | Mounts the Fast DDS profile (read-only) |
| `-e FASTDDS_DEFAULT_PROFILES_FILE=/opt/ros/fastdds-profile.xml` | Makes ROS 2 / Fast DDS use this profile |
| `-e ROS_DOMAIN_ID=0` | ROS 2 domain id |
| `-v .../my-work:/workspace` | Mounts your workspace into the container |
| `timedatectl set-timezone` | Syncs the container timezone to the host timezone |

### 5.1 Verify container ↔ host communication

Both the container and the host must load the same Fast DDS profile (see
[section 6](#6-why-the-session-disables-shared-memory)). `start-qt-container.sh`
already handles the container side; on the host, point `FASTDDS_DEFAULT_PROFILES_FILE`
at a copy of `fastdds-profile.xml`.

In the container, run the publisher:

```bash
ros2 run demo_nodes_cpp talker
```

Expected output:

```text
Publishing: 'Hello World: 1'
Publishing: 'Hello World: 2'
...
```

On the host, in a separate terminal, run the listener:

```bash
source /opt/ros/rolling/setup.bash
export FASTDDS_DEFAULT_PROFILES_FILE=/path/to/fastdds-profile.xml
export ROS_DOMAIN_ID=0
ros2 run demo_nodes_cpp listener
```

Expected output:

```text
I heard: 'Hello World: 1'
I heard: 'Hello World: 2'
...
```

### 5.2 Port-mapped mode and device configuration

The application uses a `[Device]` configuration that mixes two kinds of entries:

- **`IP;Port`** entries (`SPC_Address`, `RCU_Address`, `RDP_Address`,
  `IOServer1_Address`, `IOServer2_Address`) — the app **connects out** to those
  devices. No host→container port mapping is needed; the container just needs
  outbound network access.
- **Port-only** entries — other devices **connect in** to the app running inside
  the container. These ports must be published from the host to the container:

  ```ini
  SyncMCmdPort=61001
  FwdFlashQtrmPort=61002
  ```

  → host ports `61001` and `61002` are mapped to container ports `61001` and
  `61002`.

- **IP-only** entries (`Switch1Address`, `Switch2Address`,
  `IDRACServerAddress`, `SyncServerAddress`) — outbound only, no mapping.

`start-qt-container.sh` uses `--net=host`, which bypasses port mapping entirely
(the container shares the host network, so every port is reachable). When
testing without `--net=host`, use `start-qt-container-portmap.sh`:

```bash
./start-qt-container-portmap.sh
```

It is identical to the host-network script but replaces `--net=host` with:

```bash
-p 61001:61001
-p 61002:61002
```

> Note: without `--net=host`, ROS 2 discovery between the container and the
> host does not work over multicast. Use the `--net=host` script if you need
> container↔host ROS 2 communication.

The same setup is available via Docker Compose:

```bash
# Host network variant (matches start-qt-container.sh)
docker compose up -d
docker exec -it rqt-based-env bash

# Port-mapped variant (matches start-qt-container-portmap.sh)
docker compose -f docker-compose-portmap.yml up -d
docker exec -it rqt-based-env bash

docker compose down       # stop and remove
```

Both files use `cgroup: host` (the Compose equivalent of `--cgroupns=host`) so
systemd can boot. `docker-compose.yml` uses `network_mode: host`; the
`docker-compose-portmap.yml` variant publishes the two device ports instead.

## 6. Why the session disables shared memory

By default, ROS 2 (Fast DDS) enables a **Shared Memory (SHM)** transport as part
of its built-in transports for intra-host communication. The `/dev/shm` of a
Docker container is **isolated** from the host, so relying on shared memory to
move data between the container and the host is unreliable.

### Symptoms

With default settings you typically see:

- `ros2 topic list` and `ros2 node list` work (discovery succeeds).
- `ros2 topic echo` receives nothing (no data flows).

**Root cause:** `--net=host` makes DDS believe the container and the host nodes
are on the same machine, so Fast DDS selects its shared-memory transport. That
transport does not work across the container boundary, while discovery over UDP
still succeeds — hence the "topics visible but no data" symptom.

`fastdds-profile.xml` prevents this:

```xml
<transport_descriptors>
  <transport_descriptor>
    <transport_id>udp_transport</transport_id>
    <type>UDPv4</type>
  </transport_descriptor>
</transport_descriptors>

<participant profile_name="default" is_default_profile="true">
  <rtps>
    <userTransports>
      <transport_id>udp_transport</transport_id>
    </userTransports>
    <useBuiltinTransports>false</useBuiltinTransports>
  </rtps>
</participant>
```

- `<useBuiltinTransports>false</useBuiltinTransports>` removes the default
  transport stack (shared memory **and** built-in UDP).
- The only remaining transport is the user-defined **UDPv4**
  (`udp_transport`).

The result: data between the container and the host is transferred over **UDP**
using host networking (`--net=host`) instead of shared memory.

### Both sides must load the profile

The profile must be loaded on **both** the host and the container. If only the
container forces UDP while the host keeps the default transport stack, the two
sides negotiate incompatible transports and no data flows.

- **Container** — already handled by `start-qt-container.sh` via
  `FASTDDS_DEFAULT_PROFILES_FILE=/opt/ros/fastdds-profile.xml`.
- **Host** — export the variable pointing to a copy of the profile:

  ```bash
  export FASTDDS_DEFAULT_PROFILES_FILE=/path/to/fastdds-profile.xml
  ```

Do the profiles have to be identical? **Yes (recommended).** Technically only the
side using Fast DDS and suffering from the shared-memory issue needs UDP forced,
but using the same profile everywhere makes behavior predictable and avoids
subtle discovery/data-path mismatches.

## 7. Alternative: use Cyclone DDS instead of Fast DDS

Instead of disabling Fast DDS shared memory, you can switch the RMW
implementation to **Cyclone DDS**, which is generally more reliable with Docker.
Cyclone DDS must be selected on **both** the host and the container.

### 7.1 Install Cyclone DDS (host and container)

```bash
sudo apt-get update
sudo apt install ros-rolling-rmw-cyclonedds-cpp
```

### 7.2 Configure the container

Start the container without the Fast DDS profile mount (nothing to disable when
using Cyclone DDS). Same systemd-as-init pattern as section 5:

```bash
#!/bin/bash

# Grant local X server access
xhost +local:docker

docker run -d --rm \
  --name rqt-based-env \
  --net=host \
  --ipc=host \
  --privileged \
  --cgroupns=host \
  --tmpfs /run \
  --tmpfs /run/lock \
  --tmpfs /tmp \
  -v /sys/fs/cgroup:/sys/fs/cgroup:rw \
  -e DISPLAY=$DISPLAY \
  -v /tmp/.X11-unix:/tmp/.X11-unix \
  --gpus all \
  --device=/dev/dri \
  -e NVIDIA_DRIVER_CAPABILITIES=all \
  -e ROS_DOMAIN_ID=0 \
  -v /home/trungnb/workspace/my-work:/workspace \
  rqt-based-env:latest \
  /sbin/init

docker exec -it rqt-based-env bash
```

Then inside the container, run the publisher:

```bash
source /opt/ros/rolling/setup.bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_DOMAIN_ID=0
ros2 run demo_nodes_cpp talker
```

### 7.3 Configure the host

In a separate terminal on the host, run the listener:

```bash
source /opt/ros/rolling/setup.bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_DOMAIN_ID=0
ros2 run demo_nodes_cpp listener
```

## 8. Troubleshooting checklist

| Check | Command |
| --- | --- |
| Same ROS version | `echo $ROS_DISTRO` |
| Same domain | `echo $ROS_DOMAIN_ID` |
| Same DDS | `echo $RMW_IMPLEMENTATION` |
| Profile loaded | `echo $FASTDDS_DEFAULT_PROFILES_FILE` |
| Topics visible | `ros2 topic list` |
| Discovery works | `ros2 node list` |
| Firewall | Disable temporarily for testing |

The most common failure is the shared-memory issue described in
[section 6](#6-why-the-session-disables-shared-memory): `ros2 topic list` works
but `ros2 topic echo` receives nothing.
